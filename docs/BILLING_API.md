# Tax, invoices, purchasing and margins (Phase 2): design and API contract

Shared contract between the API (`Tourvex-API`) and the admin (`Tourvex-NextJS`). If you must deviate, change this file in the same change and say so. Phase 1 (stock) is in `docs/STOCK_API.md` and is already live.

## Decisions (agreed with the business owner)
- **Taxes at launch:** UAE VAT 5% (TRN), India GST 5/12/18% (CGST+SGST within a state, IGST between states; GSTIN; SAC/HSN), Saudi VAT 15%, UK VAT 20%, EU VAT (per-country standard rates as editable rows) and a **configurable "any country" table** so staff can add any country's tax name, rate(s) and registration label in the admin.
- **Which tax applies: by the country where the service is delivered** (a Dubai activity gets UAE VAT, a Kerala tour gets India GST, regardless of where the customer lives). Online bookings always use the automatic rule. For bookings staff create by confirming an enquiry (Phase 1 `POST /admin/stock/enquiry-bookings`), staff can choose the tax country/rate, place of supply and the buyer registration number in the confirm dialog (invoices are issued the moment a booking is paid, so there is no later override window; a wrong invoice is fixed with a credit note).
- **Invoices:** one invoice per booking, created automatically on payment (already happens), **emailed to the customer as a PDF** automatically (idempotent) and resendable from the admin; UAE-style **tax invoice** format with TRN, VAT breakdown and sequential numbers; credit notes for refunds (already exist) keep the same tax breakdown.
- **Supplier cost, profit and margin per booking** and per product; **supplier purchase invoices / stock purchases** that add stock automatically (using the Phase 1 stock engine).
- All of this is **configuration, not legal advice**: rates, labels and formats live in editable tables so the company's accountant can adjust them.

## Honest scope limits (state these in the UI help text where relevant)
- Invoices are issued in the **booking currency (AED)**. A separate INR/SAR invoice currency with FX is NOT part of this phase.
- No government e-invoicing integrations (India IRN/e-way, Saudi ZATCA phase 2, UAE FTA e-invoicing). Fields needed later are stored (GSTIN, SAC, place of supply, registration numbers). For `qr: 'zatca'` regimes the PDF carries the ZATCA phase-1 TLV QR (seller, VAT number, timestamp, total, VAT) only.
- Purchases record supplier invoices and stock received; supplier payment tracking is limited to a `paid` flag and date.

## Data model (Mongo; unique keys and indexes required; all money in the base currency, stored as numbers with 2 decimals, computed in integer minor units)

### `tax_regimes` (admin editable; seeded, never overwritten by the seed)
`{ id, country (ISO 3166-1 alpha-2), countryName, taxName ('VAT'|'GST'|any string), invoiceTitle ('Tax Invoice'), registrationLabel ('TRN'|'GSTIN'|'VAT No'), model: 'single' | 'india_gst', rates: [{ code, label, percent (0-100, max 3 decimals), isDefault }] (exactly one default, codes unique, `zero` allowed), serviceCode?: { label ('SAC'|'HSN'), value, description }, pricesIncludeTax: boolean (default false: listed prices exclude tax), numbering: { prefix: 'INV', creditPrefix: 'CN', includeCountry: boolean, yearDigits: 2|4, sequenceDigits: 4-8, maxLength?: number (India: 16) }, invoiceNotes?: string, qr: 'none'|'zatca', active, createdAt, updatedAt }`. Unique on `country` among active regimes. `model: 'india_gst'` splits the chosen rate into CGST + SGST (half each) when the supply is within the seller's state and IGST (full rate) otherwise.

### `seller_registrations` (the legal entities that issue invoices)
`{ id, country, legalName, registrationNumber (TRN/GSTIN/VAT no.), address, state?, stateCode? (India 2-digit GST state code), email, phone, website, bankDetails?, isDefault: boolean (exactly one), active }`. The seller used for an invoice = the active registration whose `country` equals the tax country, else the default registration. The seeded default is built from the existing settings (`general.legalName`, `general.taxNumber`, address).

### Tax determination (pure function `determineTax`, unit tested)
Input `{ serviceCountry, customerCountry?, customerState?, customerStateCode?, regimes, sellers, override? ({ country?, rateCode?, placeOfSupplyState? }) }` -> `{ regimeId, country, taxName, model, rateCode, percent, components: [{ code: 'VAT'|'CGST'|'SGST'|'IGST', label, percent }], sellerId, placeOfSupply: { country, state?, stateCode? }, serviceCode?, zeroRated: boolean, fallback: boolean }`. If no active regime matches `serviceCountry` the **default regime** (UAE, or `tax settings.defaultCountry`) is used and `fallback: true`. Country for each product: activity -> its destination country (see the activity schema/location; default 'AE'), holiday -> `country`, cruise -> `departureCountry`, event -> `country`, visa -> `country`. Money rounding: tax per document is computed once on the taxable amount and split across components with a largest-remainder rule so components always sum to the total tax; credit notes split their tax across the same components proportionally and the credit notes of one booking add up exactly to the invoice.

### Invoice (existing `invoices`; ADD, backwards compatible: legacy documents without these fields still render as before. NOTE: the breakdown object is named `taxInfo`, not `tax`, because the legacy numeric `tax` (tax amount) and `taxPercent` stay exactly as they are)
`title`, `taxInfo: { regimeId, country, taxName, model, rateCode, percent, components: [{ code, label, percent, taxableAmount, taxAmount }], placeOfSupply, serviceCode?, reverseCharge: false, pricesIncludeTax }`, `buyer: { name, email, phone?, address?, country?, state?, stateCode?, registrationNumber? }`, expanded `seller` snapshot (`+ sellerId, registrationLabel, registrationNumber, country, state, stateCode, bankDetails?`), `email: { status: 'pending'|'sent'|'failed'|'skipped', to?, lastSentAt?, attempts: number, lastError?, messageId? }`. Everything is a snapshot taken at issue time and is immutable afterwards.
Numbering: regime `numbering` decides the format, e.g. UAE `INV-2026-000001` (unchanged for existing numbering), India `INV-IN26-000001`-style within `maxLength` (India 16 chars max), one gap-free counter per (seller registration, document type, year), created atomically. Credit notes: `CN-...` with the same rules.

### Booking additions
`taxCountry, taxRegimeId, taxRateCode, taxPercent, taxComponents[], taxOverride?: { country?, rateCode?, placeOfSupplyState?, buyerRegistrationNumber?, reason, by, at }`, and cost snapshot `cost: { unitCost, quantity, total, currency, source: 'policy', at } | null`. Checkout prices every line with the per-line rate from `determineTax` (service country of the item) instead of one global percent; the cart/pay API shapes do not change (the total still includes tax) and public prices stay as they are (`pricesIncludeTax` false by default).

### Purchasing (`src/purchasing/`)
- `suppliers`: `{ id, name, legalName?, country, registrationNumber?, email, phone, address, paymentTermsDays, currency, notes, active, createdAt, updatedAt }`. Unique on `name` (case-insensitive).
- `purchases`: `{ id, number ('PUR-YYYY-000001', gap-free counter), supplierId, supplierName (snapshot), supplierInvoiceNumber, invoiceDate, dueDate?, currency, lines: [{ itemId (stock item id "type:ref:variant"), title, variantLabel, quantity (units added PER DAY), dateFrom, dateTo, weekdays? (0=Sunday..6), unitCost, taxPercent?, lineTotal }], subtotal, taxTotal, total, status: 'draft'|'received'|'paid'|'void', receivedAt?, paidAt?, notes, createdBy, createdAt, updatedAt }`. Unique on `(supplierId, supplierInvoiceNumber)` when the supplier invoice number is present. A line adds `quantity` units to the item's capacity on every date in `[dateFrom, dateTo]` matching `weekdays` (all days when omitted), max 93 days per line; total units = quantity x number of dates; `lineTotal = totalUnits x unitCost`.

## Admin API (all under `/api/v1/admin`, bearer auth, `Cache-Control: no-store`; new permissions below; audit-log every mutation)
Permissions: add modules `tax` (`tax.read`, `tax.write`) and `purchasing` (`purchasing.read`, `purchasing.write`). super_admin/admin: all; finance: tax.read+write, purchasing read+write, plus existing finance/invoices; operations: purchasing read+write, tax.read; sales/support/content: none (sales keep `invoices.read` if they have it). Follow `src/admin/permissions.ts`. Menu (`src/admin/menu.ts`): group **Purchasing** (`/admin/purchasing`) with **Purchases** (`/admin/purchasing`) and **Suppliers** (`/admin/purchasing/suppliers`), gated by `purchasing.read`; the tax settings live inside Settings (permission `tax.read`/`tax.write`, shown as a "Tax & invoicing" tab), and **Margin** is a report under Reports.

### Tax
- `GET /tax/regimes` -> `{ items: Regime[] }`; `POST /tax/regimes`; `PATCH /tax/regimes/:id`; `DELETE /tax/regimes/:id` (409 `REGIME_IN_USE` when any invoice/booking uses it: deactivate instead).
- `GET /tax/sellers` -> `{ items: Seller[] }`; `POST /tax/sellers`; `PATCH /tax/sellers/:id`; `DELETE /tax/sellers/:id` (409 `SELLER_IN_USE` when invoices exist; the default seller cannot be deleted).
- `GET /tax/settings` -> `{ defaultCountry, defaultRateFallbackPercent }`; `PATCH /tax/settings`.
- `POST /tax/preview` body `{ country, state?, stateCode?, amount, rateCode?, pricesIncludeTax? }` -> `{ determination, net, components: [{code,label,percent,taxAmount}], taxTotal, total, seller }` for the settings UI calculator.
- `GET /tax/countries` -> a small static list `{ code, name }[]` for pickers.
- **Enquiry confirm gains tax inputs** (extends Phase 1 `POST /admin/stock/enquiry-bookings`): optional `tax: { country?, rateCode?, placeOfSupplyState?, placeOfSupplyStateCode? }` and `buyer: { name?, address?, country?, state?, stateCode?, registrationNumber? }`. The `totalAmount` staff enter is what the customer pays (**tax-inclusive**): the tax is extracted from it (`net = total / (1 + rate)`, components split with the largest-remainder rule) so the customer-paid total never changes. Without `tax` the automatic rule (service country of the product) applies. The response adds `tax` (the determination) and the created `invoiceNumber`.

### Invoices (extend the existing admin invoice endpoints in `src/crm/billing`; reuse them, do not duplicate)
- `GET /invoices` list rows gain `taxCountry`, `taxName`, `emailStatus`; `GET /invoices/:id` returns the full new document; `GET /invoices/:id/pdf` returns the PDF (regime-specific layout).
- `POST /invoices/:id/email` body `{ to?: string (defaults to the buyer email) }` -> `{ sent: boolean, to, status, attempts }`; permission `invoices.write` (or the existing invoice permission used for edits); rate limited; 409 `EMAIL_NOT_CONFIGURED` when no SMTP is configured (nothing is lost; status stays `pending`).
- Credit notes are emailed automatically when created for a refund (same status tracking) and resendable the same way.
- Customer download keeps working through the existing booking invoice PDF endpoint.

### Purchasing
- `GET/POST /purchasing/suppliers`, `GET/PATCH/DELETE /purchasing/suppliers/:id` (409 `SUPPLIER_IN_USE` when purchases exist; deactivate instead). List supports `q`, `active`, `page`, `limit`.
- `GET /purchasing/purchases?status=&supplierId=&from=&to=&q=&page=&limit=` -> `{ items: PurchaseRow[], pagination, totals: { count, total } }`.
- `POST /purchasing/purchases` creates a **draft** (validates item ids against stock items, dates, quantities, costs); `GET /purchasing/purchases/:id`; `PATCH /purchasing/purchases/:id` (draft only, 409 `NOT_EDITABLE`).
- `POST /purchasing/purchases/:id/receive` -> in ONE transaction adds the units to every date (ledger rows type `adjust_add` with reason `Purchase PUR-...` and a `purchaseNumber` in meta), sets `status: received`, sets each item's policy `unitCost` to this purchase's unit cost (last cost) with a ledger row, refreshes stock status/caches (use the Phase 1 stock services; never bypass them). Idempotent (second call returns 200 with the same purchase).
- `POST /purchasing/purchases/:id/void` -> allowed for draft/received; for received it removes the units again unless that would drop any date below committed units (409 `STOCK_BELOW_COMMITTED` with `date` and `committed`); sets `void`.
- `POST /purchasing/purchases/:id/mark-paid` body `{ paidAt?, reference? }` -> `paid` (only from `received`).
- `GET /purchasing/summary` -> `{ draftCount, receivedUnpaidTotal, overdueCount, last30DaysTotal }` for a small dashboard card.

### Margin
- Reports use the existing reports framework (`src/admin-reports`, `/admin/reports/:name`): add **`margin`**: query `{ from, to, groupBy: 'product'|'day'|'month'|'type', productType?, supplierId? }` -> `{ rows: [{ key, title, bookings, units, revenueExTax, taxTotal, cost, margin, marginPct, bookingsWithoutCost }], totals }` and the usual CSV export, permission `finance.read`. Revenue ex-tax = booking total minus tax (refunded amounts are subtracted proportionally). Bookings without a cost snapshot are counted in `bookingsWithoutCost` and excluded from margin%.
- `GET /bookings/:id` (admin) gains `tax` (the snapshot) and, only when the caller has `finance.read`, `financials: { revenueExTax, taxTotal, total, cost: number|null, margin: number|null, marginPct: number|null }`.

## Email (needed for "invoice emailed as PDF" and for the Phase 1 stock alerts)
There is currently only a log-only provider in `src/notifications`. Add a real **SMTP provider** (nodemailer) selected when `SMTP_HOST` is set: env `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` (true/false), `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM` ("Karnish Tourism <no-reply@...>"); validated in `src/config/env.validation.ts`, documented as placeholders in `.env.example`, never logged. Mailpit is in `docker-compose.yml` for local testing (host `localhost`, port `1025`, no auth, web UI `8025`). Emails: booking confirmation with the invoice PDF attached, credit note, stock alert (`NotificationsService.stockAlert`). HTML + plain text, escaped content only, no personal data in logs (references only), sending never blocks or fails a booking/refund, failures are recorded on the invoice (`email.status = 'failed'`) and retried by a sweep (max 5 attempts, backoff) alongside the existing reconciliation sweep.

## Non-negotiables
- Money math in integer minor units; components always sum to the total; credit notes of a booking sum to its invoice; rounding rules unit tested for UAE, India (CGST/SGST/IGST odd-paisa case) and a generic regime.
- Invoice and credit-note numbers are gap-free and unique per (seller, type, year) even under concurrency; documents are immutable snapshots.
- Existing invoices (legacy) and the existing public cart/pay/booking APIs keep working unchanged.
- Idempotent everywhere: repeated webhook/sweep/receive/email calls never duplicate documents, stock or emails.
- Seeds (`npm run seed:tax`) are idempotent and never overwrite admin edits.

## Implementation notes (purchasing/margin, as built)

Where this section differs from the text above, this section wins.

### Purchasing API
- All responses are `no-store`. Errors are `{ statusCode, code, message, ... }` at the body root. `GET` needs `purchasing.read`, every mutation `purchasing.write`, every mutation is audit-logged (`supplier.*`, `purchase.*`; an idempotent repeat of receive / void / mark-paid writes no audit entry). Roles: finance, operations, admin, super_admin have both; nobody else. All of them also have `stock.read` (the line item picker calls `GET /admin/stock/items`).
- Lists (`suppliers`, `purchases`) take `q`, `page` (default 1) and `limit` (**default 25, max 200**) and return `{ items, pagination: { page, limit, total, pages } }`; purchases also return `totals: { count, total }` over the whole filter (void purchases are left out of `count` and `total` unless `status=void` is requested).
- **Supplier**: `{ id, name, legalName, country, registrationNumber, email, phone, address, paymentTermsDays, currency, notes, active, createdAt, updatedAt }`. `country` is a 2-letter ISO code (upper-cased). `name` is unique ignoring case (409 `SUPPLIER_EXISTS`). `DELETE` returns `{ deleted: true, id }`; 409 `SUPPLIER_IN_USE` when any purchase exists. Unknown id: 404 `SUPPLIER_NOT_FOUND`. An inactive supplier cannot get new purchases (409 `SUPPLIER_INACTIVE`).
- **PurchaseRow**: `{ id, number, supplierId, supplierName, supplierInvoiceNumber, invoiceDate, dueDate|null, currency, lineCount, totalUnits, subtotal, taxTotal, total, status, receivedAt|null, paidAt|null, createdAt }`. **Purchase** (the BARE object returned by `GET /purchases/:id`, `POST`, `PATCH`, `receive`, `void`, `mark-paid`; no wrapper) = row + `lines`, `paymentReference|null`, `voidedAt|null`, `notes`, `createdBy`, `updatedAt`. Dates are `YYYY-MM-DD` strings; `receivedAt`/`paidAt`/`voidedAt` are ISO instants. Unknown purchase id: 404 `PURCHASE_NOT_FOUND`.
- **Line** in requests: `{ itemId, quantity (int 1..1,000,000, units PER DAY), dateFrom, dateTo, weekdays? (0..6, unique), unitCost (max 2 decimals), taxPercent? (0..100, max 3 decimals) }` and nothing else (unknown fields are a 400). In responses the server adds `title`, `variantLabel` (snapshot of the stock item), `totalUnits` (= quantity x matching dates) and `lineTotal` (= totalUnits x unitCost, integer minor units). `taxPercent` is informational: `taxTotal` = sum of line taxes, `total = subtotal + taxTotal`. Max 50 lines, max 93 days per line.
- **Create** (`POST /purchases`): body `{ supplierId, supplierInvoiceNumber?, invoiceDate, dueDate?, currency?, lines[], notes? }`. `dueDate` defaults to `invoiceDate + supplier.paymentTermsDays` (none when the terms are 0). Only the base currency `AED` is supported (400 `CURRENCY_NOT_SUPPORTED`). Line dates in the past: 400 `PAST_DATE`. Item ids are validated against the stock items (400 `INVALID_ITEM_ID`, 404 `ITEM_NOT_FOUND`); range errors use the stock codes (`INVALID_DATE`, `INVALID_RANGE`, `RANGE_TOO_LARGE`, `NO_MATCHING_DAYS`). Duplicate `(supplierId, supplierInvoiceNumber)`: 409 `DUPLICATE_SUPPLIER_INVOICE`. The number `PUR-YYYY-000001` (Dubai year) comes from a counter incremented INSIDE the insert transaction (counter `purchase-YYYY` in `counters`), so a failed create never leaves a gap.
- **PATCH** `/purchases/:id`: drafts accept any create field (`lines` replaces all lines; an empty `supplierInvoiceNumber`/`dueDate` clears it). **Received and paid purchases accept a notes-only PATCH** (`{ notes }`); any other field there, and any PATCH on a void purchase, is 409 `NOT_EDITABLE`.
- **Receive** (`POST /purchases/:id/receive`, 200): one transaction takes the stock capacity locks, claims `draft -> received`, applies every line through the Phase 1 per-date `add` edit (`StockAdminService.applyDaysInSession`, the same code as `PUT /items/:id/days`, so `STOCK_BELOW_COMMITTED` / `UNLIMITED_ITEM` rules apply), writes ledger rows `adjust_add` (reason `Purchase PUR-...`, `meta.purchaseNumber`, `meta.purchaseId`) and sets each item's policy `unitCost` to the LAST line cost for that item with a ledger row of the new type **`set_cost`** (no date, `meta: { purchaseNumber, unitCost, previousUnitCost }`). After the commit the stock flags and caches are refreshed. Idempotent and safe under concurrency (a repeat or concurrent call returns the received purchase with 200 and changes nothing). Errors: 409 `UNLIMITED_ITEM` (an item with no capacity set cannot receive units: set a default capacity first; the whole receive rolls back), 400 `PAST_DATE`, 409 `NOT_RECEIVABLE` (void purchase), 404 `ITEM_NOT_FOUND`.
- **Void** (`POST /purchases/:id/void`, 200): draft or received (paid: 409 `NOT_VOIDABLE`). A received purchase takes its units out again (`adjust_remove`, reason `Purchase PUR-... voided`) unless a date would drop below its committed units: 409 `STOCK_BELOW_COMMITTED` with `date`, `committed`, `capacity`, nothing changes. The item unit cost is not rolled back. Repeat on a void purchase: 200, no change.
- **Mark paid** (`POST /purchases/:id/mark-paid`, 200): body `{ paidAt? (ISO date or date-time, default now), reference? }`; stores `paidAt` and `paymentReference`. Only from `received` (409 `NOT_PAYABLE`); repeat on a paid purchase: 200, no change.
- **Summary** (`GET /purchasing/summary`): `{ draftCount, receivedUnpaidTotal (status received), overdueCount (received with dueDate before today, Dubai), last30DaysTotal (received + paid purchases with invoiceDate in the last 30 days incl. today) }`.
- **Stock ledger**: `GET /admin/stock/movements` accepts `purchaseNumber` (e.g. `PUR-2026-000001`): rows whose `meta.purchaseNumber` matches, or whose `reason` starts with `Purchase <number>`. The movement type list gains `set_cost`.
- Permissions and menu: `purchasing.read` / `purchasing.write`; menu group `purchasing` (icon key `purchasing`, href `/admin/purchasing`) with children `purchasing-purchases` (Purchases, `/admin/purchasing`) and `purchasing-suppliers` (Suppliers, `/admin/purchasing/suppliers`, icon key `purchasing`).

### Cost snapshot on bookings
`booking.cost = { unitCost, quantity, total, currency, source: 'policy', at } | null` is written once when a booking is confirmed (online payment `confirmOrderBookings` inside the order transaction, the legacy single-booking `confirmPayment`, and `createEnquiryBooking` inside the enquiry transaction), from the item's policy `unitCost` x `quantity` (`src/bookings/booking-cost.ts`). `null` = the item had no unit cost then; the field is absent on bookings confirmed before this release (they count as "without cost" in the margin report). Never recomputed.

### Margin report
- `GET /admin/reports/margin` (permission `finance.read`) and `GET /admin/reports/margin/export.csv` (`finance.read` + `finance.export`). Query: the usual `range` (`7d|30d|90d|ytd`) or `from`/`to` (Dubai days, at most 366), plus `groupBy` (`product` default, `day`, `month`, `type`), `productType` (booking service type: `activity|holiday|cruise|event|visa|transfer|hotel|flight`), `supplierId` (bookings of the stock items that appear on received or paid purchases of that supplier).
- Response `{ range, currency: 'AED', groupBy, definition, rows: [{ key, title, bookings, units, revenueExTax, taxTotal, cost, margin, marginPct, bookingsWithoutCost }], totals: { same fields without key/title }, excludedNonAed }`. `key`: `type:slug` for `product`, `YYYY-MM-DD`, `YYYY-MM`, or the service type; `title` is the booking title (the key itself for day/month). Rows: by day/month ascending, by product/type by revenue descending (max 500).
- Bookings are those confirmed (`confirmedAt`) in the range in AED. Cancelled or refunded bookings whose units went back to stock (`stockReleased: true`) are not sales and are excluded.
- Per booking: tax = sum of the tax snapshot components, else the invoice tax, else 0 (never above the total); retained share = `(total - refundedAmount) / total`; `revenueExTax = (total - tax) x share`, `taxTotal = tax x share` (each rounded to 2 decimals per booking). `cost` = cost snapshot total, counted only for bookings that have one. `margin` = revenue ex-tax of the costed bookings minus cost; **`marginPct` is a percentage number (42.5 means 42.5 %)** of that same revenue, `null` when no booking in the row has a cost. `bookingsWithoutCost` counts the rest (their revenue is in `revenueExTax` but not in margin).
- `GET /admin/bookings/:id` gains `stockItemId` (`type:ref:variant` or null; for everyone with `bookings.read`) and, only with `finance.read`, `financials: { revenueExTax, taxTotal, total, cost: number|null, margin: number|null, marginPct: number|null }` (same math, one booking).

### Deviations from the contract text
- Currency of purchases: AED only. `PurchaseRow.totalUnits` was added. Draft PATCH plus notes-only PATCH on received/paid purchases (see above). `set_cost` movement type and the `purchaseNumber` movements filter are additions to Phase 1 (no existing behaviour changes). The cost snapshot uses the booking `currency` (AED) and the policy unit cost as is.
- `PUT /items/:id/days` is unchanged; its transaction body is now `StockAdminService.applyDaysInSession`, shared with purchasing.

## Implementation notes (tax/invoices/email, as built)

### Deviations and clarifications
- **`taxInfo`, not `tax`** on the invoice document (the numeric `tax` / `taxPercent` stay, still filled). `GET /invoices` rows and `GET /invoices/:id` carry: `title`, `taxCountry`, `taxName`, `emailStatus`, `taxInfo` (`regimeId, country, taxName, model, rateCode, percent, components[{code,label,percent,taxableAmount,taxAmount}], placeOfSupply, serviceCode, reverseCharge, pricesIncludeTax`, or `null` on legacy documents), `buyer` (or `null`), `email` (`status, to, lastSentAt, attempts, lastError, messageId`, or `null` on legacy documents) and the expanded `seller` snapshot (`sellerId, legalName, address, taxNumber, registrationNumber, registrationLabel, country, state, stateCode, email, phone, website, bankDetails`). Credit notes carry the same objects; their components add up exactly to the invoice.
- Admin booking view (`GET /admin/bookings/:id`) gains `taxInfo` (`country, taxName, model, rateCode, percent, components[{code,label,percent,taxAmount}], placeOfSupply, serviceCode, fallback, zeroRated, override|null`); `null` for bookings from before the tax module. Stored booking fields: `taxCountry, taxRegimeId, taxName, taxModel, taxRateCode, taxPercent, taxComponents[{code,label,percent,taxableAmount,taxAmount}], taxPricesIncluded, taxPlaceOfSupply, taxServiceCode, taxSellerId, taxFallback, taxOverride, invoiceBuyer`.
- Tax settings live in their own collection `tax_settings` (single document `key: 'tax'`). Without a document, `defaultCountry` is `AE` and `defaultRateFallbackPercent` is the existing commerce `taxPercent` (env `CHECKOUT_TAX_PERCENT`, default 5), so an unseeded database prices exactly as before.
- **Regimes**: `POST` accepts `countryName` optionally (derived from `/tax/countries`; 400 `COUNTRY_NAME_REQUIRED` if the country is not in the list). `PATCH` is partial; `country` cannot change (400, the field is not accepted); `serviceCode: null` clears the service code, `invoiceNotes: ""` clears the notes. Errors: 400 `INVALID_RATES` (exactly one default, unique codes), 400 `NUMBERING_TOO_LONG` (the longest possible number would exceed `maxLength`), 409 `REGIME_COUNTRY_EXISTS`, 409 `REGIME_IN_USE`, 404 `REGIME_NOT_FOUND`.
- **Sellers**: required `country, legalName, registrationNumber`; optional `address, state, stateCode (2 digits), email, phone, website, bankDetails (max 500), isDefault, active`. One ACTIVE registration per country (409 `SELLER_COUNTRY_EXISTS`: a number series must never have two issuers). The first registration becomes the default; making another one default moves the flag. 400 `DEFAULT_REQUIRED` when deactivating or unsetting the default, 409 `SELLER_IS_DEFAULT`, 409 `SELLER_IN_USE` (also for the registration that owns the pre-regime counters).
- **Preview** `POST /tax/preview` returns `{ determination, pricesIncludeTax, net, components[{code,label,percent,taxAmount}], taxTotal, total, seller: { id, legalName, registrationNumber, registrationLabel, country } | null }`.
- **Enquiry confirm** `POST /admin/stock/enquiry-bookings`: new optional `tax: { country?, rateCode?, placeOfSupplyState?, placeOfSupplyStateCode? }` and `buyer: { name?, address?, country?, state?, stateCode?, registrationNumber? }`. The response gains `tax: { country, taxName, percent, rateCode, components[{code,label,percent}] }` next to `booking` and `invoiceNumber`. `totalAmount` is tax-inclusive: the booking stores `subtotal` = net, `tax` = extracted tax, `total` = the entered amount, and the invoice is marked "prices include tax".
- The tax country of a holiday or event is its `country` text and of a cruise its `departureCountry`, mapped to an ISO code from the static list (names or codes, a few aliases such as UAE or UK). Anything that cannot be mapped, and every activity, is taxed as `AE`. Visas are not sold through checkout.
- India: with no place of supply (online bookings) the supply is treated as within the seller state (CGST + SGST). Staff choose another state in the enquiry confirm to get IGST.

### Numbering
`{prefix}-{COUNTRY?}{YY|YYYY}-{sequence zero padded}` (credit notes use `creditPrefix`): UAE `INV-2026-000001` (unchanged), India `INV-IN26-000001`. One counter per (seller, series), where the series is the number prefix including the year, so each series is gap-free. The counter increment and the invoice insert run in ONE transaction (a failed insert rolls the number back). The seller that existed before regimes (`numberingScope: 'legacy'`) keeps the original `inv-YYYY` / `cn-YYYY` counters for the original format, so the existing sequence continues. `maxLength` is checked when a regime is saved and again when a number is issued.

### Tax at checkout
Each cart item is priced with the rate of `determineTax` for its service country (activities: `AE`) and keeps the determination server side (`CartItem.taxInfo`, never in the cart JSON). The booking snapshots it at order creation and the invoice is built from that snapshot. Public cart, pay and quote shapes are unchanged (`taxesAndFees` is still included in the total). A regime with `pricesIncludeTax: true` extracts the tax from the listed price instead of adding it.

### Email
- Provider selected by `SMTP_HOST` (nodemailer): `SMTP_HOST, SMTP_PORT, SMTP_SECURE, SMTP_USER, SMTP_PASS, MAIL_FROM` (required when `SMTP_HOST` is set). Without it nothing is sent and `POST /admin/invoices/:id/email` answers 409 `EMAIL_NOT_CONFIGURED`.
- Every new invoice or credit note gets `email: { status: 'pending', attempts: 0, to }` (`skipped` without a recipient) and is sent right after creation in the background (never blocks or fails the booking or refund). Failures set `failed` + `lastError` (addresses redacted) and are retried by a sweep on the same timer as the order reconciliation (every 5th checkout tick, 5 minutes by default, off when `NODE_ENV=test`) with backoff 5 min, 20 min, 80 min, about 5.3 h, at most 5 attempts, for documents of the last 7 days. An atomic lock (`email.lockedUntil`) prevents double sends.
- `POST /admin/invoices/:id/email` body `{ to? }` returns `{ sent, to, status, attempts }`; permission `invoices.write`, 10 per minute; 400 `NO_RECIPIENT`; a failed send answers 200 with `sent: false, status: 'failed'`. Resending a `sent` document sends it again.
- Templates (HTML + text, all dynamic content escaped): booking confirmation with the invoice PDF, credit note, stock alert (`NotificationsService.stockAlert`).

### Commands
`npm run seed:tax` (idempotent, never overwrites), `npm run indexes:verify` (checks `tax_regimes`, `seller_registrations`, `tax_settings`).
