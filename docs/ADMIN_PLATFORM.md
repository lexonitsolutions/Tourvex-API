# Admin platform: architecture and conventions (Phase 0, the foundation)

The travel CRM / website admin lives at `/admin` inside the Next.js app (`Tourvex-NextJS`) and uses the NestJS API (`Tourvex-API`, base `/api/v1`).
This doc is the shared contract for all later admin modules (bookings, enquiries CRM, support tickets, vouchers/QR, catalog/content, blog, customers/B2B,
finance/invoices, dashboard/reports, integrations, settings, staff/audit). Phase 0 delivers: RBAC, audit log, staff management, site settings, the admin shell and shared UI kit.

## Auth and RBAC
- Staff sign in with Clerk like customers; the API resolves the local user (existing guard) and its `roles[]` (`Role` enum: customer, b2b_*, content, sales, operations, finance, support, admin, super_admin).
- **Permissions** are strings `<module>.<action>`, mapped from roles in ONE file `src/admin/permissions.ts` (static map, unit tested). Modules: dashboard, bookings, enquiries, tickets (support), vouchers, customers, partners (b2b), catalog, blog, promos, reviews, finance, invoices, integrations, settings, staff, audit.
  Actions: read, write, delete, export, plus specific ones (bookings.refund, bookings.cancel, vouchers.validate, staff.assign_roles, finance.reconcile, ...).
  Suggested mapping (adjust with justification): super_admin all; admin all except `staff.assign_super_admin`; sales = dashboard.read, enquiries.*, customers.read/write, bookings.read, partners.read, promos.read; operations = bookings.read/write/cancel, vouchers.*, catalog.read, enquiries.read; finance = bookings.read, finance.*, invoices.*, bookings.refund, dashboard.read, customers.read; support = tickets.*, bookings.read, customers.read, reviews.*, enquiries.read; content = catalog.*, blog.*, promos.*, reviews.*, dashboard.read.
- Decorator `@RequirePermission('bookings.read')` (guard reads permissions from the user's roles; 403 otherwise). Existing `@Roles()` routes keep working; new admin routes use permissions. No permission is ever granted from client-supplied data.
- `GET /admin/me` → `{ user: {id, name, email, roles[]}, permissions: string[], menu: MenuItem[] }`, where the server builds `menu` (id, label, href, icon key, children?) from permissions so the UI never shows what the API would reject. Non-staff (customer) → 403.

## Audit log
- Collection `audit_logs`: `at`, `actorId`, `actorEmail`, `actorRoles`, `action` ("booking.cancel"), `entityType`, `entityId`, `summary` (short text), `changes` (field-level `{field, from, to}` with sensitive keys redacted: anything matching /password|token|secret|card|key/i), `ip` (hashed with a server salt), `requestId`. No personal data beyond ids/emails of staff.
- Decorator/interceptor `@Audited('entityType', 'action')` for admin mutations plus a service method `AuditService.record(...)` for manual calls. Failed attempts to do forbidden things (403) are not logged; successful mutations always are.
- `GET /admin/audit` (audit.read; admin, super_admin): filters actor, entityType, entityId, action, date range, `q`; paging; newest first. Immutable: no update/delete endpoints; TTL none.

## Staff management (staff.read / staff.write / staff.assign_roles)
- `GET /admin/staff` (filter role/status/q, paging), `POST /admin/staff` `{ email, fullName, roles[] }` (creates/updates the local user by email; Clerk account links on first sign-in by verified email, same provisioning as customers), `PATCH /admin/staff/:id` `{ fullName?, roles?, active? }`, `POST /admin/staff/:id/deactivate|reactivate`.
- Rules: only super_admin may grant/revoke `admin` or `super_admin`; the last active super_admin cannot be deactivated or demoted; staff cannot change their own roles; deactivated staff get 403 everywhere; every change audited. Customers/B2B users are not staff (role set must include at least one staff role to appear here).

## Site settings (settings.read / settings.write)
- Collection `site_settings` (one doc per `group`): groups `general` (siteName, supportEmail, supportPhone, address, socials), `commerce` (taxPercent, holdMinutes, fxMarkupPercent, bookingCutoffHours), `notifications` (sender name, templates for booking confirmation, voucher, cancellation: subject/body with `{{placeholders}}` whitelist), `homepage` (ordered section toggles). Validation per group (class-validator), `updatedBy/At`.
- `GET /admin/settings/:group`, `PUT /admin/settings/:group`, `GET /settings/public` (public, cacheable, only safe fields: siteName, support contact, socials). Existing env-driven values (CHECKOUT_TAX_PERCENT, CHECKOUT_HOLD_MINUTES, FX_MARKUP_PERCENT) remain the defaults; when a DB value exists the services read it through one `SettingsService.get()` with in-memory cache (60s) so ops can change without redeploys. Wire checkout tax/hold and the currency markup to it, keeping tests green.

## API conventions for every admin endpoint
- Lists: `GET /admin/<module>?q=&page=&limit=(default 20, max 100)&sort=field:asc|desc&<filters>` → `{ items, pagination:{page,limit,total,pages} }`; details `GET /admin/<module>/:id`; mutations return the updated entity. Errors `{statusCode, code, message}`.
- CSV export `GET /admin/<module>/export.csv` with `<module>.export` permission, same filters, max 10,000 rows, streamed, formula-injection-safe (prefix cells starting with = + - @ with a quote), audited.
- Internal notes/timeline pattern (reused by bookings, enquiries, tickets, customers): `notes: [{ id, at, authorId, authorName, text (<=2000) }]` appended via `POST /admin/<module>/:id/notes`.
- All admin routes: not cached, throttled generously, excluded from the CurrencyInterceptor (path segment `admin` is already excluded). Money in admin is always AED unless a field says otherwise.

## Admin shell and UI kit (frontend)
- Routes under `app/admin` (outside the `(market)` group, own layout/CSS prefix `adm-`, `noindex`). Clerk sign-in required; `GET /admin/me` drives menu and route guards; 403 page for non-staff; forbidden pages show a clear "no access" state.
- Layout: dark-navy collapsible sidebar (grouped menu from `/admin/me`, active state, collapsed icon rail, mobile off-canvas), topbar (global search placeholder wired later, quick create menu, notifications placeholder, profile menu with sign out), breadcrumbs, page header with actions, content area. Our brand tokens (navy/teal, Barlow Condensed headings, Barlow body as elsewhere) but a calm, dense, data-first look (not the marketplace look).
- Shared kit in `app/admin/_kit` (plain JS components + CSS): AdminShell, PageHeader, DataTable (server-side paging/sorting, column visibility, row selection + bulk bar, sticky header, skeleton/empty/error states, URL-synced filters), FilterBar, StatCard, Sparkline/Bar/Line/Donut charts (small own SVG components, no heavy chart library), StatusBadge, Tabs, Drawer, Modal, ConfirmDialog (typed confirmation for destructive actions), Form fields (text, textarea, select, multiselect, date/range, switch, money, rich-text-lite for blog later), Toast, Timeline (notes/audit), Avatar, Pagination, Dropdown menu, EmptyState, KeyValue list, CopyButton, CSV export button helper. All keyboard accessible, ARIA correct, motion = transform/opacity only (respect the project's motion policy), responsive (tables degrade to cards under 760px).
- API client `app/admin/_lib/adminApi.js` (token via `useApp().getAccessToken()`, error mapping, abort support), `useAdminMe()` context, `can(permission)` helper.
- Phase 0 pages: `/admin` (placeholder dashboard using the kit with real counts from `/admin/summary`), `/admin/staff`, `/admin/audit`, `/admin/settings` (tabs per group), plus a **kit gallery** at `/admin/_kit` only in development. The existing `/admin/leads` and `/admin/inquiries` pages (browser-storage leads) stay working, linked as "Leads (legacy)", until the CRM phase replaces them.
- `GET /admin/summary` (dashboard.read): small counts (bookings today/pending, open enquiries, open tickets, new customers 7d) computed from existing collections (return 0 for modules not built yet).

## Implementation notes (API, Phase 0)
- **Shapes.** `GET /admin/me` → `{user:{id,name,email,roles}, permissions, menu}`; any staff role may call it, non-staff get `403 {code:'NOT_STAFF'}`. `GET /admin/summary` → `{bookings:{today,pending}, enquiries:{open}, tickets:{open}, customers:{new7d}}` (`today` = created since 00:00 UTC; open enquiries = visa + cruise + event enquiries whose status is not `closed`; tickets always 0). Staff view: `{id, fullName, firstName, lastName, email, roles, active, status, linkedToClerk, createdAt, updatedAt}`; lists are `{items, pagination}`. Settings: `GET` returns `{group, values, isDefault, updatedAt, updatedBy}`; `PUT` takes the complete group object as the body (it replaces the stored one, unknown keys are a 400 `VALIDATION_FAILED`) and returns the same view. POST staff actions return 201 (Nest default), PUT/PATCH 200.
- **Deactivation** is a new `active` boolean on `users` (default true; legacy documents without it count as active), separate from the existing `status`. The auth guard and `OptionalUserResolver` honour both; changes invalidate the identity cache on the instance that made them, other instances converge within 60 s (the same as roles).
- **Extra staff rules beyond the doc:** only a super_admin may change or (de)activate a user that currently holds `admin`/`super_admin`; nobody may deactivate themselves; PATCH `roles` must keep at least one staff role (removing all staff access = deactivate); `POST /admin/staff` on an existing user keeps their non-staff roles (customer, b2b_*) and replaces their staff roles; a new staff record also gets `customer`. The last-super_admin rule is checked before writing and re-verified after (the write is reverted with a 409 if two demotions raced).
- **Settings** defaults: `general`/`notifications` have built-in text defaults, `homepage.sections` defaults to `[]` (the frontend decides the section ids; ids are lowercase slugs, order is render order). `commerce.bookingCutoffHours` is stored and validated but not enforced by any booking flow yet. Template placeholders allowed: bookingRef, customerName, serviceName, travelDate, totalAmount, voucherUrl, cancellationReason, siteName, supportEmail. `CurrencyService.markupPercent` is now a synchronous getter over the last settings snapshot (refreshed in the background after 60 s) because the response interceptor cannot await; checkout/catalog `await` the settings directly.
- **Audit** writes never fail the request (a failed write is logged server-side). `ip` is an HMAC-SHA256 with `AUDIT_IP_SALT` (falls back to a value derived from `CLERK_SECRET_KEY`); it is stored but never returned by the API. Immutability is enforced at the API (no routes) and in the Mongoose schema (update/delete hooks); a direct database client can still alter the collection.
- **Helpers for later modules:** `src/common/query/paging-query.dto.ts` (`PagingQueryDto`, `parseSort`, `buildPagination`), `src/common/csv/csv.ts` (`streamCsv`, 10,000-row cap, formula-injection safe, UTF-8 BOM), `src/common/notes/notes.ts` (`NoteSchema`, `AddNoteDto`, `buildNote`, `appendNote`), `@Audited(entityType, action)` + `AuditInterceptor` + `setAuditContext(req, {...})` in `src/audit/audited.ts`.
- **Bootstrap:** `npm run seed:staff -- --email <email>` (see the README).
